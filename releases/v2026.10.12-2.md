## What changed in Live Guard 2.42

### Charging watts come back on phones whose current counter reports nothing

The OPPO A3s regression: 2.40/2.41 showed `0.00 W` and `-0.00 A` while charging, even though the
same phone's charge history recorded real 4.6–4.8 W sessions. The app read the battery current
**only** from `BatteryManager.BATTERY_PROPERTY_CURRENT_NOW`, and older/OEM kernels (Android
8.1/ColorOS among them) answer that with `0` or "unsupported" while the battery broadcast extra
the broadcast's `current_now` extra still carries the real charge current. `4.36 V × 0 A` then
looked like a measurement. (Android only exposed that key as `BatteryManager.EXTRA_CURRENT_NOW`
in API 34, so the literal is used — minSdk is 26.)

Now one policy decides which current reading may be used and records **where it came from**:
a real non-zero property value first, then the broadcast extra, then a broadcast zero (a genuine
trickle/full reading), and otherwise nothing. A bare property `0` with no broadcast
corroboration is *not* reported as 0 A, because on those kernels it means "unsupported" — and an
unsupported sensor is still never rendered as `0.00 W`. Units are still decided in exactly one
place and never inferred from magnitude; watts are still computed in exactly one place. When the
broadcast rescued the reading, the screen says so instead of implying every phone exposes the
documented counter.

This is a **fallback, not a promise**: if a kernel puts no current in the broadcast either, the
reading is reported as *not measured* instead of a fake zero. Which of the two the A3s does is
exactly what the owner's device test will show, and it is listed as open work above rather than
as a proven fix.

### Voice A and Voice B are chosen for you

The *"Choose and preview two voices…"* error is gone — the string was removed from the catalog
with its Tamil pair so it cannot come back. When no choice is saved, the first two usable
installed voices for that answer's language become Voice A and Voice B; with only one, both
slots use it; with none, nothing is spoken and the voice diagnostics say why instead of an error
in the chat. Tamil and English stay separate. The Voice & daily watch card remains, now stating
that A/B are automatic and can be previewed or swapped there — and a **manual** save still
requires a completed preview and two distinct voices. Each answer is still read once, in its
assigned voice.

### The status-bar meter and the background monitor come back after an update

Both now default **ON** (opt-out), and an app update or a reboot re-arms them even when the
switch was never tapped — previously the boot receiver read a preference nobody had written and
left the meter dark. One policy object owns these defaults, shared by the DataStore flow, the
plain-prefs mirror a service reads and the UI state, which used to carry three separate literal
`false` values and could disagree. A saved OFF is still an OFF and is never overwritten;
Settings now says that turning one off is a choice, not a failure. The hourly health watch is
armed by the monitor's own switch too, not only by voice and the daily check.

The **floating pill stays opt-in on purpose**: Android needs "Display over other apps" before
anything can be drawn beside the clock, and that access is never granted automatically, so
defaulting it ON would promise a reading the phone has not allowed. Automatic *online* daily
summaries also stay a separate explicit consent, default OFF.

### Security check: preinstalled system apps included by default

The "Include preinstalled system apps" switch in the Security screen now defaults ON, and the
security review scope and app-cache scope read the same policy object so the three cannot drift.
Inclusion is **inspection only**: no permission is granted, nothing is selected or removed
automatically, and an unchecked or unknown hash still proves nothing. A hit on a read-only
preinstalled partition is information, not an available action.

### "Manage" opens the app's own permission page, not a ROM hub

On the SMS/banking-SMS findings, **Manage** used to open MIUI's app-level "Other permissions" hub
instead of that app's permission page. Two causes: the generic all-permissions action was fired
first (MIUI claims it and ignores the package), and the package travelled only as an extra, never
as the intent's `package:` data URI. Routes are now ordered ROM-aware — the ROM's own
package-scoped editor first on a Xiaomi, then the editor for the **exact** permission, then the
app's whole permission list, then App info as the guaranteed last resort — and every candidate
carries the package both ways. ColorOS is recognised and gets its own manual path. No OEM
component name was invented: a ROM that does not expose a candidate simply fails to resolve and
the next one is tried, ending in the existing honest manual-path text. **Routing differs per ROM
and per release, so this still needs checking on the Xiaomi and the OPPO.**

### Main screen: one spacing scale, nothing clipped

The home list had **no top padding at all**, so the first card was drawn flush against the header
and the LED strip — the clipping in the owner's screenshot. The screen also mixed four
hand-picked edges (14/16/14/16 dp) with card padding at 12/14/16 dp. One 4 dp-based scale now
owns every edge, gap and card padding: one screen edge, an even card gap raised from 14 to 16 dp
so rows no longer crowd, a real top inset, and two card-padding sizes only. This is a *layout*
contract — whether nothing clips at the largest font scale, on a small screen or in split screen
still needs a phone.

### One language for the whole screen

Cards could render the opposite language from the header, and one line stayed English in both.
Two causes: `tr()` read the process-wide language while some composables read the ViewModel's
copy, with nothing keeping them equal; and a card that observes no state (the update card) was
skipped by Compose on a toggle, so it kept text composed in the old language. There is now one
authority, resolved from the saved choice **before** the first composition and updated on every
toggle, and the screen tree is rebuilt on a toggle so every string re-reads it. Every display
site moved off the copy and onto the authority; the state copy now exists only to trigger that
rebuild, and the build fails if a display site reads it again.

The work list reported *"Verified in-app download; Android confirms installation."* as missing a
Tamil pair. It was **not** missing — it has been in the catalog since the update card shipped,
and a test now asserts that it and the other four named cards have real Tamil values. That line
rendered English because of the recomposition bug above. Adding a second pair would have failed
the duplicate-key gate; the correction is recorded in
[`docs/live-guard-2.42-scope.md`](../docs/live-guard-2.42-scope.md) so it is not "fixed" again.

### Publication rule: device evidence only for a new dangerous permission

The repository's own device-evidence gate changed, by explicit owner decision, and the reason is
written down in [`AGENTS.md`](../AGENTS.md), [`PUBLISHING.md`](../PUBLISHING.md) and the
changelog. A release newer than 2.39/code44 now needs
`docs/live-guard-<version>-device-evidence.md` **only when it adds a dangerous permission**
versus the previously published release APK, compared on the built artifacts with `aapt2` by
`tools/verify_release_permission_delta.py`. Appop/signature-level declarations such as
`MANAGE_EXTERNAL_STORAGE` and `SYSTEM_ALERT_WINDOW` are correctly **not** counted as runtime
prompts. The tool fails closed: an unreadable previous release means "evidence required".

Everything else about the old rule is unchanged and still enforced: when an evidence file
*does* exist, publication still requires the Play Protect and installer wording, still reads
`TESTED-APK-SHA256`/`TESTED-RUN-ID`, and still publishes only a rebuild that reproduces the
recorded digest byte-for-byte — otherwise it promotes the recorded run's verified artifact, so a
rebuilt digest can never inherit an earlier device test. Play Protect was not disabled, bypassed
or worked around; the package name and signing key were not changed; the 2.39 install-block
advisory and the 2.40/2.41 evidence records are intact.
