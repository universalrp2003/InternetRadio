# Live Guard / CleanSweep 2.40 (core, no notification reading) — CANDIDATE, NOT PUBLISHED

> **This release is prepared but not published.** Core 2.40 removes the notification
> reader completely. Publishing those bytes requires the owner's physical-device
> installation result with Play Protect **on**, recorded against the exact APK SHA-256 in
> `docs/live-guard-2.40-device-evidence.md`; the CI publication step refuses a CleanSweep
> version newer than 2.39 without it. Nothing here is Google Play/F-Droid approval or
> all-device certification.

**Candidate:** Live Guard / CleanSweep **2.40 / versionCode 45**, package
`com.universalrp.cleansweep`, unchanged stable signing key, minSdk 26, target/compileSdk 36.

**Last published release (unchanged, assets immutable):** 2.39 / code44, tag
`v2026.10.11-3`, source `6790a96b591b5a3215f5f28193726f0cd607c04f`, CI run 38143638654,
`CleanSweep-v2.39.apk` 44,610,589 bytes, SHA-256
`f29daac53da8e45cc8f278a93f7ffe9c78d36136f13497d16d93fb6f6fa89b98`.

## Why this candidate exists

Google Play Protect blocked installation of the published APK on the affected phone
("App blocked to protect your device"). The leading suspect is the opt-in notification
reader added in 2.38/2.39, because
`BIND_NOTIFICATION_LISTENER_SERVICE` and the `NotificationListenerService` intent filter
are **declared in the package** — switching the feature off at runtime does not remove
them. Details and the honest limits:
[`docs/live-guard-play-protect-install-block.md`](../docs/live-guard-play-protect-install-block.md).

## What changed

### The reader is gone, not disabled

- No `MessageReaderService`, no notification-listener binding/permission, no
  `NotificationListenerService` intent filter, no reader screen, no reader route, link or
  setup row.
- The reader-only ML Kit `translate`/`language-id` dependencies and the reader
  service-label resources are removed.
- The 2.39 reader sources are archived byte-for-byte under
  `docs/archived-notification-reader-2.39/` — historical reference only, never compiled,
  never a hidden flavor or module, never distributed as a workaround. Re-introducing any
  notification/message access needs a separate owner decision plus policy and device
  review.
- The retired pure policy now lives in the test source set, so its 12 historical cases
  still run without shipping the capability. CI rejects the retired class names in **both**
  debug and release APK DEX, and validates the source **and merged** manifests.

### One-time cleanup of 2.39 leftovers

`CorePrivacyMigration` runs on IO from app start and retires only: the
`liveguard_notification_reader` preferences file, the `voice_messages` key, the old voice
diagnostics **only** when their last event was the reader's, and the obsolete `reader`
skipped-reminder id. It writes an idempotent completion marker only after every step
succeeds and logs nothing private. It does **not** reset API keys, language, A/B voice
selections, any switch (including saved OFF), the data plan, charging/security histories,
permission-review records or other apps' data. Previously downloaded public translation
model files may remain unused in private storage.

### Everything else is kept

- Ordinary Live Guard alerts and speech: battery low/full, charging card, thermal,
  storage, unplug, network change, security, daily brief, setup reminders, manual read
  aloud, installed-voice previews and the two selected/previewed A/B answer voices (one
  voice per answer, each answer read once, with the installed-voice offline retry).
- `POST_NOTIFICATIONS` for Live Guard's **own** alerts stays, as does the verified in-app
  updater with its `FileProvider` and mandatory Android installer confirmation.
- Battery/phone health with the labelled estimated-phone-age badge, user-selected cleanup
  and system-app review, include-system default ON when unset with saved OFF preserved,
  cache refresh on open with no new automatic selection/deletion, compact Battery/Data/
  Phone widgets, genuine observed unplug time/level, unchanged floating pill, honest
  permission-review dates, and the six insights features (truthful dated dashboard, safe
  compatibility diagnostics, opt-in security history, observed charging history, data
  budgeting/history, reviewed grounded action checklists).
- EN/TA parity with 12-hour AM/PM human-visible times; TODAY-only, deduplicated news;
  cancellable chat (45s incl. 8s web), 15s checks/models, 90s heavy operations with
  progress, cancel, late-result suppression and no hidden provider fallback.

### Bilingual notice

Both languages now state in Settings and feature setup that core Live Guard does not read
other apps' notifications or messages and declares no notification-listener, SMS,
Contacts, call-log, Accessibility or device-admin capability, while ordinary Live Guard
alerts remain.

## Verification

Required before publication: **301 cases in each** Cleaner debug/release variant
(**33 suites**), `:radio:testDebugUnitTest`, all-module debug/release APK/AAB gates,
package/version/API-26/non-debuggable/stable-signature/packaged-feature checks, the retired
capability/DEX rejection gate, and the measured universal APK size (must fit both the
updater's 128MiB cap and the existing 2.39 client's 50MiB bound). Companion apps
(Ramesh Radio 1.8, PulseEQ 1.2) keep their exact previously verified bytes.

The exact candidate APK digest, CI run and the owner's device result are added to this file
only after they exist. Older releases (2.38, 2.39, 2.37 and earlier) are never overwritten
and their historical CI records are never erased.
