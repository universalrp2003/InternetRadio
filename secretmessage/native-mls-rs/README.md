# mls-rs / AWS-LC feasibility lane (TEST ONLY)

This separate harness evaluates the published **mls-rs 0.56.0** MLS implementation with the project's **AWS-LC provider 0.25.0**, restricted to `CipherSuite::CURVE25519_AES128` (the RFC 9420 X25519 / AES-128-GCM / SHA-256 / Ed25519 suite). Hosted run [38679021757](https://github.com/universalrp2003/InternetRadio/actions/runs/38679021757) passed formatting, the two-member fixture (including ciphertext tamper rejection, fresh next-generation recovery, replay rejection, and rejection of a same-label KeyPackage with an unpinned signing key), Clippy, JNI host check, Android dependency inspection, license-metadata inventory, RustSec, four-ABI APK build, and API 35 emulator smoke. The license inventory checks that resolved packages declare Cargo license expressions or point to license files; it is not legal compatibility approval or a complete notice review. GitHub marks both steps successful and the check annotations show no RustSec warning, but the raw audit log and `secretmessage-mls-rs-candidate-review` artifact could not be downloaded from this workspace because the Actions result-storage host is inaccessible here. Therefore the per-crate RustSec diagnostics and exact license declarations from this latest run remain unreviewed; do not infer zero advisories or legal compatibility from the step result alone. Earlier run [38664410994](https://github.com/universalrp2003/InternetRadio/actions/runs/38664410994) also passed and reported no RustSec findings in its generated candidate lockfile. An initial negative-test attempt in [38669823568](https://github.com/universalrp2003/InternetRadio/actions/runs/38669823568) incorrectly retried the exact same message generation after a failed tamper and got `KeyMissing(0)`; the fixture now tests a fresh next-generation message instead. This is an observed test-path behavior, not a security finding or a general delivery/retry guarantee. It reuses only the existing small JNI entry point and standalone smoke APK; the protocol implementation and crypto provider come from upstream crates. The candidate is not linked into the Secret Message product application.

The upstream project is actively maintained and publishes Apache-2.0-or-MIT licensed crates. Its README explicitly says it has not received a full third-party security audit. Its provider table marks AWS-LC as stable and RustCrypto as experimental; this lane uses AWS-LC and does not enable experimental post-quantum suites. The manifest enables AWS-LC's upstream `bindgen` feature for Android cross-compilation; no cryptographic code is patched. Those upstream statements are not an audit of the resolved dependency graph or an endorsement for this product.

The harness runs a synthetic two-member, in-memory group and serializes MLS messages at the simulated transport boundary. It checks bidirectional application-message round trips, absence of test plaintext in the wire bytes, rejection of a modified ciphertext in both directions, acceptance of a fresh next-generation message after each rejected ciphertext, and rejection of replayed messages after successful delivery. It deliberately does not assume that retrying the exact same MLS ciphertext after a failed decryption will succeed. The fixture also uses a test-only exact-`SigningIdentity` allowlist to reject a forged KeyPackage that reuses Bob's `BasicCredential` label with a different signing key. The labels and pinset are synthetic; this does not implement QR/safety-code exchange, real-device identity, or a production trust system. These assertions exercise this pinned candidate's message-processing path only; they are not a general cryptographic review. The smoke bridge is a minimal test-only JNI wrapper; it does not validate the upstream UniFFI wrapper, which is coupled to the OpenSSL provider in this release. A Kotlin product integration would still need a reviewed wrapper/provider design. This test does not validate real device identity, persistent key protection, network delivery, two-phone interop, or message-expiry behavior.

The optional `storage-spike` Cargo feature is a separate **host-only** SQLCipher experiment. Its test explicitly calls the upstream `Group::write_to_storage()` after the commit and after sending, stores the MLS group state through the SQLCipher provider, closes and reconstructs the client, reloads the group, and proves a fresh message still decrypts on the other fixture member. mls-rs documents that group changes are not persisted automatically until this explicit call; a product must prove it checkpoints every relevant state/ratchet mutation without creating message-history persistence. It also checks that a fixed test-only plaintext marker is absent from the database bytes and that an incorrect database key cannot reopen the state. The Android JNI feature does not enable SQLCipher; CI inspects both dependency graphs and inventories/audits the combined candidate lockfile. This narrow result does not persist or protect the signing identity, exercise Android Keystore wrapping, verify flash-level erasure, backup/migration or power-loss recovery, cross-compile SQLCipher for Android, or establish that this storage design is fit for the product. The fixed database key exists only in the test fixture.

CI will record the generated lockfile, run both the in-memory host fixture and the optional host-only SQLCipher persistence/restart experiment, run Clippy/RustSec and a Cargo license-metadata inventory, inspect the Android and host-only storage dependency graphs separately, build the standalone APK for four Android ABIs, and launch the fixture on a hosted API 35 emulator. Even if those feasibility checks pass, this does not grant security/release approval. Keep all RustSec findings visible; do not ignore advisories or use this candidate for sensitive communications. No product integration or publication is authorized by this test lane.
