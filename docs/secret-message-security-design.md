It renders a local chat UI with a custom QWERTY/symbol keyboard and freehand canvas; preview content stays in Compose memory and local echoes expire after 60 seconds. It has no networking, MLS integration, identity, signaling, persistence, or remote peer, and it prominently says it is not secure. It sets `FLAG_SECURE` as a best-effort deterrent, not a guarantee. ## Owner-selected product direction

- App title: **Secret Message**.
- One-to-one conversations; the two devices must be online at the same time. Do not queue messages for offline recipients.
- Direct peer connection when possible, with a short-lived signaling path and encrypted relay fallback when NAT/firewalls prevent direct connection.
- Pairing/identity check by QR or a human-compared safety phrase. The code verifies a cryptographic device identity, not a legal name or a biological human.
- Custom in-app English QWERTY plus a freehand canvas. The canvas transmits strokes, not recognized words; it is language-flexible but cannot guarantee communication without any language barrier. Any future handwriting-to-text must run locally, without uploading text or images.
- Six original bundled notification-tone choices. Notifications must not reveal message text.
- Message content should live only in memory and expire within 60 seconds of authenticated delivery/display on both phones. The current preview starts its local timer at Send and expires its local echo; production must start the receiver's timer only after successful authenticated delivery.
- No chat history, message database, message backups, advertisements, analytics, content logs, third-party keyboard, clipboard export or message content in notifications.
- Enable Android `FLAG_SECURE` on sensitive screens, as a deterrent only. It cannot prevent a second-device camera, every OEM/OS capture path, a rooted phone, or a compromised operating system.
- Optional Android biometric/device-credential app lock is local to that phone. Do not transmit biometric data.

## Threat model and honest limits

Protect message contents against network observers, an untrusted signaling/relay service, and accidental local retention. Authenticate the peer's public key so an attacker cannot silently substitute a device during rendezvous. Minimize connection metadata and keep signaling/session state short-lived.

This does not prove a verified name or real-world identity. A QR/safety-code comparison confirms that both parties have the same public key; the parties still need to check who they are meeting. A local biometric confirms local device access, not the remote user's identity. No Android app can guarantee a recipient will not photograph the screen with another device or use a modified/compromised phone. Network peers and relays may learn IP addresses, timing, and traffic volume even when they cannot decrypt content.

## Protocol research and current gate

### OpenMLS baseline (blocked; research-only)

The initial isolated feasibility spike uses **OpenMLS 0.9.0**, pinned to the `openmls-v0.9.0` release; OpenMLS is not approved or selected for product integration. An isolated crate in `secretmessage/native/` contains a two-member, in-memory smoke harness using the RustCrypto provider and an RFC 9420 ciphersuite. The provider itself is not covered by SRLabs' audit and is not approved for production. The spike is not linked to the Android preview. Its two-member host test, Clippy, four-ABI JNI builds, and standalone APK checks passed CI; run [38589530783](https://github.com/universalrp2003/InternetRadio/actions/runs/38589530783) also completed that in-memory fixture in a hosted Android emulator. The published 0.9.0 RustSec audit blocks that baseline lane on two lockfile advisories in an optional dependency. The harness does not verify real identities or connected devices and is not permission to claim the app is secure or publish a production chat.

Reasons for the spike: OpenMLS implements the IETF Messaging Layer Security protocol (RFC 9420) and is MIT-licensed. SRLabs performed an independent audit sponsored by the Sovereign Tech Agency, but it is important not to overstate what that means: the reviewed OpenMLS commit was `a3402f2` from 2025-10-22, not the later 0.9.0 release, and the report explicitly excludes both crypto providers, storage providers, and delivery-service/client examples. The report lists eight findings: the High MAC-authentication issue and three Medium issues are marked mitigated; one Low issue is marked acknowledged; one informational DoS issue is risk-accepted; the other Low and informational findings are marked mitigated. The audit announcement says one Low fix was still in progress. Verify the current state of that finding and review changes since the audited commit before relying on 0.9.0. The chosen RustCrypto provider is outside that audit and requires separate scrutiny; also review the full resolved Rust dependency/license tree.

The important integration risk remains: OpenMLS lists Android architectures as “unsupported, but built on CI,” not tested/supported. There is no official OpenMLS Kotlin/Android SDK. CI run [38589530783](https://github.com/universalrp2003/InternetRadio/actions/runs/38589530783) installed and ran the separate test-only JNI APK on a hosted API 35 x86_64 emulator; the local two-member fixture completed successfully. This establishes emulator runtime feasibility for the selected JNI path only. It does not establish physical-device behavior, two-device interoperability, a Kotlin product bridge, WebRTC, or identity binding. The harness is not included in the Android product app. Any future product bridge must remain minimal and only call OpenMLS; do not implement protocol, key derivation, signing, or encryption ourselves. OpenMLS 0.9.0 requires Rust 1.91 or newer, so pin and reproduce the toolchain.

The first GitHub Actions run on 2026-10-14 passed the two-member host test and Clippy, but a coarse dependency-graph guard stopped before Android builds and RustSec audit. The lockfile contains 0.0.9 through the optional `hpke-rs-libcrux` 0.7.0 package, whose manifest pins that exact version, even though the package is not in the active Android normal/build graph. Cargo audit also reported the unmaintained `proc-macro-error2` 2.0.1 warning (RUSTSEC-2026-0173). No advisory was ignored. A published upstream fix now exists at the provider-package level: `hpke-rs-libcrux` 0.8.0 pins `libcrux-kem = "=0.0.10"`, and its paired `hpke-rs` 0.8.0 pins the provider at `=0.8.0`. The release is tagged from `celabshq/libcrux` commit `42d68bd`; release PR #1637 received an APPROVED review. This demonstrates an upstream release review, not an independent security audit. It does not resolve the OpenMLS 0.9.0 graph: `openmls_rust_crypto` 0.6.0 (the newest published version at review time) requires `hpke-rs` 0.7, and `hpke-rs` 0.7.0 pins `hpke-rs-libcrux = "=0.7.0"`, whose manifest still pins the vulnerable `libcrux-kem = "=0.0.9"`. Therefore Cargo cannot select the fixed 0.8 provider through the published OpenMLS 0.9.0 dependency path. Further upstream investigation on 2026-10-14, rechecked on 2026-10-15, found that OpenMLS' unreleased `main` tree has migrated `openmls_rust_crypto` to `hpke-rs` 0.8 in commit [`055a2b4`](https://github.com/openmls/openmls/commit/055a2b4b06b5) and updated its lockfile to `libcrux-kem` 0.0.10 in [`e0b21a7`](https://github.com/openmls/openmls/commit/e0b21a70a55a); the upstream full-matrix checks on that dependency-bump commit passed ([run](https://github.com/openmls/openmls/actions/runs/38123131726)). This is not a release or security audit, and that migration raises the upstream MSRV to Rust 1.94. As of the 2026-10-15 recheck, GitHub's [OpenMLS release list](https://github.com/openmls/openmls/releases) still ends at `openmls-v0.9.0`; the separate [`v0.9.1` tag](https://github.com/openmls/openmls/tree/v0.9.1) is not a GitHub release and its [provider manifest](https://github.com/openmls/openmls/blob/v0.9.1/openmls_rust_crypto/Cargo.toml) still uses `hpke-rs` 0.7. The [unreleased main lockfile](https://github.com/openmls/openmls/blob/main/Cargo.lock) also still contains `proc-macro-error2` 2.0.1; the separate candidate-lane audit below confirms that the warning persists in the resolved graph. Treat upstream main as a candidate future fix only; the published OpenMLS 0.9.0 baseline remains untouched. A separate test-only lane in `secretmessage/native-upstream/`, pinned to commit `e0b21a70a55a9014b8de2772b36bf3d638adad51`, passed its host MLS test, Clippy, JNI host check, Android dependency inspection, four-ABI APK build, hosted API 35 emulator smoke, and the standard `cargo audit` command in run [38659236776](https://github.com/universalrp2003/InternetRadio/actions/runs/38659236776). Its candidate lock resolves `libcrux-kem` 0.0.10; the audit no longer reports RUSTSEC-2026-0330/0331 but still reports `proc-macro-error2` 2.0.1 as unmaintained (RUSTSEC-2026-0173). `cargo-audit` labels this an allowed warning and returns success; CI keeps the warning visible and does not ignore it. This is limited feasibility evidence, not a clean production audit, official upstream release, independent security review, or product integration. Keep the release/security gate blocked until a compatible official release and exact production dependency graph receive clean review; do not patch or override cryptographic dependencies locally. The CI license inventory covered 197 packages with zero `UNKNOWN` license fields; it reports four `hpke-rs` packages as MPL-2.0 and the local spike crate as GPL-3.0-only. Those SPDX fields are metadata, not legal compatibility approval; keep human license/notice review as a release gate. Keep the Libcrux provider disabled, retain upstream notices, and reject draft protocol features/ciphersuites. Start with the RFC 9420 mandatory-to-implement X25519/AES-128-GCM/SHA-256/Ed25519 ciphersuite, subject to verification against the pinned OpenMLS API.

For the product shape, test a two-member MLS group only: the online device that creates the room sends setup messages to the other through the WebRTC DataChannel; only MLS application ciphertext may carry chat content. The signaling/TURN services must never receive MLS secrets or plaintext. The room is memory-only and is discarded when the session ends; no offline key-package, welcome, message or history queue is added. MLS membership/authentication must be explicitly bound to the QR/safety-code-verified device key—an invite code or WebRTC DTLS connection alone is not identity verification. Identity-key persistence/protection and peer-key-change handling remain separate work and release gates.

### mls-rs persistence and Android Keystore gate (not evaluated)

The Android JNI harness and product app do not test persistence or hardware-backed key storage. The base `android-jni` feature disables mls-rs defaults and relies on `ClientBuilder::new()` in-memory storage; it does not enable the optional SQLite provider. A separate, optional host-only `storage-spike` feature has been added to exercise the upstream SQLCipher provider and MLS group-state reload, but its first CI run has not completed, so no persistence result is claimed yet. Upstream `GroupStateStorage` warns that state writes should be atomic to avoid corrupting a group. The `KeyPackageStorage` contract states that `KeyPackageData` contains secret HPKE keys and that deletion should securely erase data. The optional upstream SQLite provider exposes SQLCipher, but it needs a caller-supplied key and is not itself an Android Keystore integration; ordinary SQLite `DELETE` is not evidence of secure erasure on flash storage. No candidate code wraps a database key with an Android Keystore key or persists signing identities. Before product integration, test atomicity, encrypted-at-rest state, key-package/epoch cleanup, backup and migration behavior, and the exact added dependency/license/RustSec graph; hardware-backed key lifecycle still requires a separate Android-specific design and test.

No custom cryptographic handshake, ratchet, cipher, or static shared-key scheme is acceptable. If no maintained MLS candidate can pass the Android native-build, two-device, identity-binding, dependency, audit-status and license gates, stop and reassess rather than weakening the security requirements or quietly swapping libraries.

### Candidate transport

Use WebRTC DataChannels for direct device-to-device traffic, with ICE/STUN and a self-controlled TURN service as a fallback. WebRTC provides transport encryption (DTLS) for DataChannel packets, but transport protection alone does not verify that the connected peer is the intended human/device. Keep an application-layer authenticated E2EE session bound to the QR-verified identity. A TURN relay should forward ciphertext only and discard it immediately; the signaling service may hold only ephemeral invitations, public connection descriptions and ICE candidates in memory. No server-side message queue or history.

No signaling or TURN service is implemented or deployed in this checkout. A future service must forward only short-lived SDP/ICE setup data, keep no message queue/history, use an owner-controlled TURN relay, and receive its own operational hardening, abuse/privacy, metadata-retention, and security review before deployment. The current Android preview has no network client and requests no network permissions.

- WebRTC protocol stack reference: <https://github.com/webrtc-rs/rtc>
- Android WebRTC package candidate: <https://github.com/webrtc-sdk/android>

No Android WebRTC client dependency has been selected or integrated. Before adding one, review its exact native AAR provenance, bundled third-party notices, maintenance/security backports, runtime quality, and license. Do not ship with a random public STUN/TURN service as a hidden dependency. The service operator, retention, IP/metadata exposure, abuse controls and costs must be decided and disclosed. The chosen direct-first design must explain that CGNAT, carrier networks and restrictive Wi-Fi can prevent a direct connection, and provide the approved encrypted TURN fallback without adding offline queues.

## Key and message lifecycle (planned)

1. Create a per-install identity key and protect private key material using Android Keystore where supported. Keep keys and minimum ratchet/session state separate from message content; device identity must not silently change after app restart.
2. Pair by scanning a QR code or comparing a safety phrase in person/over a trusted separate channel. Show a persistent warning if the peer key changes; never auto-accept a changed key.
3. Authenticate a fresh session handshake, then encrypt text/drawing before it enters the data channel. Test replay, reordering, duplicate, truncation, reconnect, stale invite and peer-key-substitution cases.
4. Send only while both users have an established authenticated session. No offline queue. Begin the recipient's 60-second expiry on successful receive/display, and clear both views on timer expiry, chat close or session end. Sender should also discard its copy on the same delivery-based TTL.
5. Keep message bodies/strokes out of disk, saved instance state, clipboard, notification preview, logs, crash reports and backups. Clear mutable buffers on a best-effort basis; JVM/Android memory wiping cannot be guaranteed.
6. The current Android preview implements only local UI/timer behavior and requests no permissions. It has no network transport, identity keys, QR scanner, notification support, camera, microphone, or contacts access. Add only the network permissions actually required by a future reviewed WebRTC/signaling client.

## App module and staged acceptance

The root Gradle build now includes `:secretmessage`, whose product shell is in `secretmessage/product/`. It is version `0.1.0-preview` with application ID `com.rpideas.secretmessage.preview`. Its current features are local-only text/drawing echoes, a custom QWERTY/symbol keyboard, an in-memory 60-second timer from the local Send/Add action, and best-effort `FLAG_SECURE`. Its source manifest declares no permissions; the preview has no network client, identity, persistence, MLS integration, or remote peer, and the CI APK gate rejects merged network permissions. The UI explicitly labels it **NOT SECURE**. The normal Build APK workflow is configured to run its pure policy unit tests and compile only the debug APK; the release/bundle and four-app publication tasks exclude it. Hosted Kotlin compilation, preview unit tests, four-app regression/build checks, and the corrected merged-APK network-permission gate passed in run [38678283393](https://github.com/universalrp2003/InternetRadio/actions/runs/38678283393). The preview remains debug-only and was not included in the four-app release artifacts. This does not count as a secure product or a testable two-phone build. After all security and physical-device gates pass, the intended app can be versioned separately and published to both `RP-Android-Apps` and `InternetRadio` with identical verified APK bytes and separate release notes. Do not distribute this preview as secure.

Before any real release:

1. Resolve the MLS library/provider gate without integrating either candidate yet. OpenMLS 0.9.0 has published RustSec blockers; its unreleased upstream dependency migration is not a release. The mls-rs 0.56.0/AWS-LC harness passes test-only host/JNI/ABI/emulator checks, but mls-rs has no full third-party audit and its latest raw RustSec/license reports remain unreviewed. Inspect the complete audit and exact production dependency/license graph, use only a reviewed upstream release, cross-compile the minimal bridge, and prove a two-device setup plus ciphertext round-trip. Reassess rather than bypassing any gate, and obtain an independent security threat model/review before production.
2. Implement identity-key lifecycle, QR/safety-code verification, key-change warnings, secure storage and app-lock policy.
3. Select, build and operationally review the short-lived signaling service; then integrate a direct-first WebRTC DataChannel client with owner-controlled TURN relay, strict no-message-retention behavior, abuse controls, rate limits and documented metadata handling. No server or client exists in this checkout, and no public server/domain/credentials have been provisioned.
4. Add authenticated, forward-secret message encryption; never rely on WebRTC DTLS alone or claim a peer's real-world identity from a QR code.
5. Add delivery acknowledgment, expiry synchronization, reconnect/cancellation handling and tests proving no offline queue or disk persistence.
6. Complete dependency/license review, vulnerability review, static/unit/instrumentation tests and independent cryptographic/security review. Test on two physical devices across Wi-Fi, mobile data, carrier NAT and router changes.
7. Audit notifications, screenshots, recording, accessibility, keyboard, recents, backups, logging and app-switch behavior. Use honest privacy claims and disclose all server/network metadata.

No step in this preview is a substitute for a professional security review. Until all release gates pass, keep the app clearly labelled **prototype/not secure** and do not trigger publication.
