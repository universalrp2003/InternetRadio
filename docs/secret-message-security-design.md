# Secret Message — security and product design

**Status:** the root Gradle build includes a separate `:secretmessage` Android preview at `secretmessage/product/`. Version 0.2.1-preview integrates the owner-approved WhisperPad product/UI modules. These are the built-in English keyboard with a large square Letter/Picture drawing pad, six synthesized tones, RAM-only chat state with the 30-second undelivered rule and 60–300-second recipient-view countdown, an optional BiometricPrompt app lock, and manifest permission-removal rules. Messaging goes through a `SecretMessageMlsTransport` boundary whose only implementation is unconnected, so nothing is delivered and each sent message disappears 30 seconds after Send. It has no networking, MLS integration, identity, signaling, message persistence, or remote peer, and it prominently says it is not secure. It sets `FLAG_SECURE` as a best-effort deterrent, not a guarantee. Do not use this preview for sensitive communication. ## Owner-selected product direction

- App title: **Secret Message**.
- One-to-one conversations; the two devices must be online at the same time. Do not queue messages for offline recipients.
- Direct peer connection when possible, with a short-lived signaling path and encrypted relay fallback when NAT/firewalls prevent direct connection.
- Pairing/identity check by QR or a human-compared safety phrase. The code verifies a cryptographic device identity, not a legal name or a biological human.
- Custom in-app English QWERTY plus a freehand canvas. The canvas transmits strokes, not recognized words; it is language-flexible but cannot guarantee communication without any language barrier. Any future handwriting-to-text must run locally, without uploading text or images.
- Six original bundled notification-tone choices. Notifications must not reveal message text.
- Message content should live only in memory and expire on both phones after a user-selected, non-disableable 60–300-second countdown that begins when the recipient views it. An undelivered sender copy expires locally after 30 seconds; no offline queue is allowed. Only authenticated delivery may start the recipient-view countdown. The 0.2.0 preview implements these rules in a unit-tested state machine. Because its transport is unconnected, no message is ever delivered: each sent message stays undelivered and is removed 30 seconds after Send. The recipient-view countdown therefore never starts in the preview, and preview expiry must not be described as recipient-view expiry.
- No chat history, message database, message backups, advertisements, analytics, content logs, third-party keyboard, clipboard export or message content in notifications.
- Enable Android `FLAG_SECURE` on sensitive screens, as a deterrent only. It cannot prevent a second-device camera, every OEM/OS capture path, a rooted phone, or a compromised operating system.
- Optional Android biometric/device-credential app lock is local to that phone. Do not transmit biometric data.

## Threat model and honest limits

Protect message contents against network observers, an untrusted signaling/relay service, and accidental local retention. Authenticate the peer's public key so an attacker cannot silently substitute a device during rendezvous. Minimize connection metadata and keep signaling/session state short-lived.

This does not prove a verified name or real-world identity. A QR/safety-code comparison confirms that both parties have the same public key; the parties still need to check who they are meeting. A local biometric confirms local device access, not the remote user's identity. No Android app can guarantee a recipient will not photograph the screen with another device or use a modified/compromised phone. Network peers and relays may learn IP addresses, timing, and traffic volume even when they cannot decrypt content.

## Protocol research and current gate

### OpenMLS baseline (blocked; research-only)

The initial isolated feasibility spike uses **OpenMLS 0.9.0**, pinned to the `openmls-v0.9.0` release; OpenMLS is not approved or selected for product integration. An isolated crate in `secretmessage/native/` contains a two-member, in-memory smoke harness using the RustCrypto provider and an RFC 9420 ciphersuite. The provider itself is not covered by SRLabs' audit and is not approved for production. The spike is not linked to the Android preview. Its two-member host test, Clippy, four-ABI JNI builds, and standalone APK checks passed CI; run [38589530783](https://github.com/universalrp2003/InternetRadio/actions/runs/38589530783) also completed that in-memory fixture in a hosted Android emulator. The published 0.9.0 RustSec audit blocks that baseline lane on two lockfile advisories in an optional dependency. The harness does not verify real identities or connected devices and is not permission to claim the app is secure or publish a production chat.

Reasons for the spike: OpenMLS implements the IETF Messaging Layer Security protocol (RFC 9420) and is MIT-licensed. SRLabs performed an independent audit sponsored by the Sovereign Tech Agency, but it is important not to overstate what that means: the reviewed OpenMLS commit was `a3402f2` from 2025-10-22, not the later 0.9.0 release, and the report explicitly excludes both crypto providers, storage providers, and delivery-service/client examples. The report lists eight findings: the High MAC-authentication issue and three Medium issues are marked mitigated; one Low issue is marked acknowledged; one informational DoS issue is risk-accepted; the other Low and informational findings are marked mitigated. The audit announcement says one Low fix was still in progress. Verify the current state of that finding and review changes since the audited commit before relying on 0.9.0. The chosen RustCrypto provider is outside that audit and requires separate scrutiny; also review the full resolved Rust dependency/license tree.

The important integration risk remains: OpenMLS lists Android architectures as “unsupported, but built on CI,” not tested/supported. There is no official OpenMLS Kotlin/Android SDK. CI run [38589530783](https://github.com/universalrp2003/InternetRadio/actions/runs/38589530783) installed and ran the separate test-only JNI APK on a hosted API 35 x86_64 emulator; the local two-member fixture completed successfully. This establishes emulator runtime feasibility for the selected JNI path only. It does not establish physical-device behavior, two-device interoperability, a Kotlin product bridge, WebRTC, or identity binding. The harness is not included in the Android product app. Any future product bridge must remain minimal and only call OpenMLS; do not implement protocol, key derivation, signing, or encryption ourselves. OpenMLS 0.9.0 requires Rust 1.91 or newer, so pin and reproduce the toolchain.

The first GitHub Actions run on 2026-10-14 passed the two-member host test and Clippy, but a coarse dependency-graph guard stopped before Android builds and RustSec audit. The revised run, [38566630494](https://github.com/universalrp2003/InternetRadio/actions/runs/38566630494), completed the host/Clippy checks, active Android dependency inspection, and native cross-builds for all four Android ABIs. Its Android normal/build graphs contained `libcrux-sha3` 0.0.10 plus `libcrux-intrinsics` 0.0.8, `libcrux-platform` 0.0.3, `libcrux-secrets` 0.0.6, and `libcrux-traits` 0.0.8. OpenMLS' RustCrypto provider 0.6.0 depends on `hpke-rs` 0.7.0, whose manifest declares `libcrux-sha3` as a non-optional dependency. This is a transitive dependency review item; its presence does not prove it is exercised by the selected ciphersuite, and it is not security clearance. The active graph did not contain the Libcrux provider packages (`openmls_libcrux_crypto` or `hpke-rs-libcrux`). That run also records successful SDK discovery, NDK 27.2.12479018 installation/linker verification, all-four-ABI cross-build, review-metadata capture, and review-artifact upload. The aggregate gate reports RustSec audit as the only failing check, making the pre-`continue-on-error` outcomes explicit.

The RustSec audit scanned 197 packages from the generated `Cargo.lock` and blocked the final gate on two findings in `libcrux-kem` 0.0.9: RUSTSEC-2026-0330 (medium, short hybrid encapsulation seed) and RUSTSEC-2026-0331 (high, short hybrid-key decoding); both advisories require `libcrux-kem` 0.0.10 or newer. The lockfile contains 0.0.9 through the optional `hpke-rs-libcrux` 0.7.0 package, whose manifest pins that exact version, even though the package is not in the active Android normal/build graph. Cargo audit also reported the unmaintained `proc-macro-error2` 2.0.1 warning (RUSTSEC-2026-0173). No advisory was ignored. A published upstream fix now exists at the provider-package level: `hpke-rs-libcrux` 0.8.0 pins `libcrux-kem = "=0.0.10"`, and its paired `hpke-rs` 0.8.0 pins the provider at `=0.8.0`. The release is tagged from `celabshq/libcrux` commit `42d68bd`; release PR #1637 received an APPROVED review. This demonstrates an upstream release review, not an independent security audit. It does not resolve the OpenMLS 0.9.0 graph: `openmls_rust_crypto` 0.6.0 (the newest published version at review time) requires `hpke-rs` 0.7, and `hpke-rs` 0.7.0 pins `hpke-rs-libcrux = "=0.7.0"`, whose manifest still pins the vulnerable `libcrux-kem = "=0.0.9"`. Therefore Cargo cannot select the fixed 0.8 provider through the published OpenMLS 0.9.0 dependency path. Further upstream investigation on 2026-10-14, rechecked on 2026-10-15, found that OpenMLS' unreleased `main` tree has migrated `openmls_rust_crypto` to `hpke-rs` 0.8 in commit [`055a2b4`](https://github.com/openmls/openmls/commit/055a2b4b06b5) and updated its lockfile to `libcrux-kem` 0.0.10 in [`e0b21a7`](https://github.com/openmls/openmls/commit/e0b21a70a55a); the upstream full-matrix checks on that dependency-bump commit passed ([run](https://github.com/openmls/openmls/actions/runs/38123131726)). This is not a release or security audit, and that migration raises the upstream MSRV to Rust 1.94. As of the 2026-10-15 recheck, GitHub's [OpenMLS release list](https://github.com/openmls/openmls/releases) still ends at `openmls-v0.9.0`; the separate [`v0.9.1` tag](https://github.com/openmls/openmls/tree/v0.9.1) is not a GitHub release and its [provider manifest](https://github.com/openmls/openmls/blob/v0.9.1/openmls_rust_crypto/Cargo.toml) still uses `hpke-rs` 0.7. The [unreleased main lockfile](https://github.com/openmls/openmls/blob/main/Cargo.lock) also still contains `proc-macro-error2` 2.0.1; the separate candidate-lane audit below confirms that the warning persists in the resolved graph. Treat upstream main as a candidate future fix only; the published OpenMLS 0.9.0 baseline remains untouched. A separate test-only lane in `secretmessage/native-upstream/`, pinned to commit `e0b21a70a55a9014b8de2772b36bf3d638adad51`, passed its host MLS test, Clippy, JNI host check, Android dependency inspection, four-ABI APK build, hosted API 35 emulator smoke, and the standard `cargo audit` command in run [38659236776](https://github.com/universalrp2003/InternetRadio/actions/runs/38659236776). Its candidate lock resolves `libcrux-kem` 0.0.10; the audit no longer reports RUSTSEC-2026-0330/0331 but still reports `proc-macro-error2` 2.0.1 as unmaintained (RUSTSEC-2026-0173). `cargo-audit` labels this an allowed warning and returns success; CI keeps the warning visible and does not ignore it. This is limited feasibility evidence, not a clean production audit, official upstream release, independent security review, or product integration. Keep the release/security gate blocked until a compatible official release and exact production dependency graph receive clean review; do not patch or override cryptographic dependencies locally. The CI license inventory covered 197 packages with zero `UNKNOWN` license fields; it reports four `hpke-rs` packages as MPL-2.0 and the local spike crate as GPL-3.0-only. Those SPDX fields are metadata, not legal compatibility approval; keep human license/notice review as a release gate. Keep the Libcrux provider disabled, retain upstream notices, and reject draft protocol features/ciphersuites. Start with the RFC 9420 mandatory-to-implement X25519/AES-128-GCM/SHA-256/Ed25519 ciphersuite, subject to verification against the pinned OpenMLS API.

For the product shape, test a two-member MLS group only: the online device that creates the room sends setup messages to the other through the WebRTC DataChannel; only MLS application ciphertext may carry chat content. The signaling/TURN services must never receive MLS secrets or plaintext. The room is memory-only and is discarded when the session ends; no offline key-package, welcome, message or history queue is added. MLS membership/authentication must be explicitly bound to the QR/safety-code-verified device key—an invite code or WebRTC DTLS connection alone is not identity verification. Identity-key persistence/protection and peer-key-change handling remain separate work and release gates.

### mls-rs persistence and Android Keystore gate (host-only evidence; product gate remains open)

The Android JNI harness and product app do not use persistent MLS storage or hardware-backed key storage. The base `android-jni` feature disables mls-rs defaults and relies on `ClientBuilder::new()` in-memory storage; it does not enable SQLite. A separate optional host-only `storage-spike` feature passed in [run 38681945215](https://github.com/universalrp2003/InternetRadio/actions/runs/38681945215). The test configures the upstream SQLCipher provider with a fixed test-only database key, calls `Group::write_to_storage()` after a commit and after sending, closes/reconstructs Alice's client, reloads the group, and resumes a message exchange. The initial attempt in [run 38681156231](https://github.com/universalrp2003/InternetRadio/actions/runs/38681156231) failed with `GroupNotFound` because the test omitted those explicit persistence calls; the follow-up passed after adding them. It also checks that the database does not expose SQLite's plaintext file header, the marker does not appear in database bytes, and a wrong database key fails to open the state. This is narrow host-side evidence that the selected SQLCipher configuration can protect and reload this fixture's MLS group snapshot; it is not Android/device/power-loss validation.

The test retains Alice's signing identity and signing secret only in test-process memory and never proves identity-key persistence. It does not wrap the database key with Android Keystore, test device hardware backing, establish a production key lifecycle, verify key-package cleanup, backup/migration or flash-level erasure, or prove the correct persist/checkpoint call is made for every production group/ratchet mutation. mls-rs documents that state changes from processing incoming messages are not persisted until `Group::write_to_storage()` is explicitly called; its `GroupStateStorage` contract also warns that writes should be atomic to avoid group corruption. The `KeyPackageStorage` contract says stored `KeyPackageData` includes secret HPKE keys and should be securely erased on deletion, but the inspected SQLite implementation uses ordinary SQL `DELETE`, which is not evidence of secure erasure on flash storage. The optional upstream SQLite provider exposes SQLCipher only when explicitly enabled and requires a caller-supplied key; it is not an Android Keystore integration.

CI kept SQLCipher out of the standard Android JNI/APK graph. After initial failures due to missing OpenSSL headers, target-prefixed `ranlib` names, and a shared Cargo build cache ([runs 38683217102](https://github.com/universalrp2003/InternetRadio/actions/runs/38683217102), [38684689429](https://github.com/universalrp2003/InternetRadio/actions/runs/38684689429), and [38687345624](https://github.com/universalrp2003/InternetRadio/actions/runs/38687345624)), follow-up [run 38688708114](https://github.com/universalrp2003/InternetRadio/actions/runs/38688708114) passed the optional SQLCipher/vendored-OpenSSL cross-build for all four Android ABIs, while the standard AWS-LC-only APK build and API 35 emulator smoke also passed. This is compile-only evidence: it does not run SQLCipher in an Android app or validate Android Keystore integration. The separate OpenSSL cryptographic library alongside AWS-LC is test-only and must receive full dependency, license, RustSec, symbol/linkage, and security review before any consideration. GitHub reports successful candidate license-metadata and RustSec steps, but the raw logs and review artifact for run 38688708114 remain inaccessible from this workspace, so exact per-crate audit findings and package declarations remain unreviewed. Before any product integration, independently review the complete feature/dependency graph and licenses, audit atomic commit/checkpoint behavior, key-package/epoch cleanup, backup/migration, and Android Keystore key wrapping; hardware-backed identity-key persistence remains a separate Android-specific design and device-test gate.

No custom cryptographic handshake, ratchet, cipher, or static shared-key scheme is acceptable. If no maintained MLS candidate can pass the Android native-build, two-device, identity-binding, dependency, audit-status and license gates, stop and reassess rather than weakening the security requirements or quietly swapping libraries.

### Safety-code verification in the LAN test (test only)

The test-only LAN APK (0.3.0-lan-test) adds the comparison step that the WhisperPad transport contract calls `VERIFYING_MLS_EPOCH_AUTHENTICATION`. After the guest joins, each phone formats the first 20 bytes of the group's RFC 9420 epoch authenticator as four groups of five digits. Each 40-bit chunk is reduced modulo 100000, as in libsignal's numeric fingerprints, giving about 66 bits. Both people compare the two screens and answer **Codes match** or **Codes differ**. The answers travel as MLS application messages, and each phone reads the other answer before continuing or closing. The fixed test messages are exchanged only if both people confirmed; a “Codes differ” answer on either phone stops both.

- **Why this value:** RFC 9420 section 8.7 describes the epoch authenticator as a value whose out-of-band comparison reveals an impersonating member. It is derived from the group context, which includes the tree hash over both members' credentials and signature keys. Using it adds no handshake, signature or commitment outside MLS.
- **Why 20 digits:** a relaying device would hold two separate groups. It controls the newest secrets of the group it creates for the joining phone, so it could try to grind that group's code to match the other group. It can only do that until the joining phone stops waiting for its Welcome (45 seconds), far short of the roughly 2^66 attempts a match needs. A short code, such as 6 digits, would not be safe without a commitment step, which MLS does not define and this design does not add.
- **Limits:** in 0.3.0 the identities were temporary for each test, so the code verified that session only. Test APK 0.4.0 adds persistent identities and remembered phones (next section). MLS validation still accepts any BasicCredential.
- **Tests:** host tests cover the code format, matching codes on both phones, PASS after two confirmations, STOPPED when either side reports a mismatch, and different codes for a relaying device's two groups. The hosted emulator still runs only the local in-memory path; the comparison needs two phones.

### Remembered test identities and key-change warnings (test only)

Test APK 0.4.0-lan-test adds the next part of release gate 2 to the same LAN test. It is a feasibility step, not the product's identity design.

- **One key per install:** on first use, the app picks a random 8-byte device ID and asks the Rust bridge for an Ed25519 MLS signing key (mls-rs with AWS-LC). The identity text (device ID, secret key and public key) is encrypted with AES-256-GCM under an Android Keystore key that never leaves Keystore, and the ciphertext is kept in app-private preferences. Backup is disabled, and uninstalling the app deletes the Keystore key and therefore the identity.
- **Device ID in the credential:** the BasicCredential label carries the device ID, so a phone can tell “the same phone with the same key” from “the same phone with a different key”.
- **Remembered phones:** after a PASS (both people confirmed the code), each phone stores the other phone's device ID and public key, read from its own MLS group, which is the state the safety code covers. On later tests the comparison screen says whether the other phone is new, remembered, or has a changed key. A changed key is shown as a red warning and must be compared again; it is never accepted silently, and the new key is stored only after another PASS. In this test the code is compared every time, even for a remembered phone with an unchanged key; whether a product may skip that step is a later design decision.
- **Test controls:** “Reset this phone's test key” creates a new key but keeps the device ID, so a remembered peer shows the warning. “Forget remembered phones” clears the list.
- **Limits:** the signing key is a software key created in the Rust bridge, not a hardware-bound Keystore signing key. It is decrypted into app memory for each test and passes through Java strings, which cannot be wiped. The remembered-phone list is stored unencrypted in app-private storage. MLS validation still accepts any BasicCredential; the remembered keys only drive the on-screen status. Hardware-backed identity, a reviewed storage and recovery design, and product integration remain open.
- **Tests:** host tests cover identity text round trips and malformed input, new/remembered/changed classification, a first meeting that remembers both phones, a second meeting that recognizes both, a host key reset that the guest flags as changed, and a relaying device whose key is flagged as changed by a host that verified the real guest.

### Typed test messages (test only)

Test APK 0.5.0-lan-test lets the two people type short messages to each other after both have confirmed the safety code and the fixed exchange has passed. It is the first time user-typed text crosses between the phones; it is still a feasibility step, not the product's messaging design.

- **Same MLS group:** each typed message is an MLS application message in the group whose epoch authenticator both people just compared. The plaintext is a kind byte, a per-phone message number and up to 1,000 UTF-8 bytes of text (the screen limits input to 300 characters). The receiving phone answers with an MLS-encrypted acknowledgment, shown as “✓ delivered”. Either person can end the typed test (an encrypted end marker tells the other phone), and it ends by itself after 10 minutes.
- **No storage:** typed text is kept only in app memory for the two screens. It is never written to storage, logs or the copied report, which lists only counts (sent, delivered, received) and how the typed test ended. Text in Java strings cannot be wiped. The input asks the keyboard not to learn from it (`IME_FLAG_NO_PERSONALIZED_LEARNING`), which keyboards may ignore. Screenshots stay allowed so testers can report results; the product must still decide on `FLAG_SECURE`.
- **Staying connected:** since Android 15, an app that starts network work outside a valid process lifecycle gets socket errors, and in practice an app loses its connections a few seconds after it leaves the screen. The test therefore keeps the screen on while a LAN test runs, asks both people to keep the app on screen from the moment the second phone joins until the result appears, and adds this explanation to errors caused by a closed connection. Leaving the app to share or paste the invite before that is fine: there is no connection yet, and in the owner's runs a host that shared the invite and came back still accepted the join. The host must be back on screen when the other phone joins.
- **Version check:** the joining phone's first frame now names the protocol version (`secretmessage-lan-test/5`) and invites carry `v=5`, so mismatched test APKs fail with a clear message instead of a confusing connection error.
- **Limits:** no offline queue, history, reconnection or expiry timers; nothing from the typed test survives the session. MLS validation still accepts any BasicCredential (see above). This does not satisfy any release gate below.

### Stopping both phones at once (test only)

The third 0.5.0 run on phones showed that a “Codes differ” answer did not reach the other phone until that phone's person had answered too: each phone waited for its own person, then sent its answer, and only then read the other phone's answer. The phone that reported the difference also waited for the other person. Had that person never answered, their phone would have timed out after two minutes and closed the connection, and the reporting phone would have shown a closed-connection error instead of STOPPED. No test message could pass in either case, because a PASS needs two confirmations, but the stop was slow and unclear. Test APK 0.5.1-lan-test changes the comparison step:

- **Watching while comparing:** while its person compares the codes, each phone keeps reading the connection in short intervals. If the other phone reports different codes, it stops at once, removes its own question from the screen and shows STOPPED. A confirmation from the other phone is kept but not shown, so it cannot nudge the person who is still comparing.
- **No waiting after a mismatch:** a phone whose person taps “Codes differ” sends that answer inside MLS, closes its sending side, gives the other phone up to two seconds to read it (reading and discarding anything that arrives, so the connection is not reset), and shows STOPPED.
- **No answer:** if a person does not answer within two minutes, their phone sends an encrypted “no answer” marker, so both phones show STOPPED and say which phone did not answer, instead of a connection error. If the other phone's connection closes during the comparison, this phone reports that at once instead of after its person answers.
- **Frames:** answers are read a piece at a time without reading past the end of the answer, so the fixed test messages that follow a confirmation are never lost.
- **Version check:** the protocol is now `secretmessage-lan-test/6` and invites carry `v=6`, so 0.5.0 and 0.5.1 phones refuse each other with a clear message.
- **Tests:** host loopback tests cover a mismatch reported while the other person never answers (with either phone reporting, both finishing within seconds rather than at the two-minute limit), a mismatch reported after the other phone confirmed, a comparison left unanswered on either phone, a late confirmation that still passes, an answer that arrives in pieces together with the start of the next frame, and the screen prompt being withdrawn so that a late tap is refused.

### Internet relay for the test build (test only)

On 17 October 2026 the owner chose the recommended option for the Internet step: a relay on a Cloudflare Worker with one Durable Object per chat room, on the owner's own free Cloudflare account (no card). - **Relay (`secretmessage/relay`):** `wss://secretmessage-relay.universalrp2003.workers.dev`. ### Remembered phones calling each other in 1.1.0 (owner decisions)

After testing 1.0.0 on two phones the owner asked that remembered phones can start a chat at any time, with a notification on the other phone, and chose (17 October 2026) “always ready, without Google”, “connect directly if the key is unchanged” and “the name only after unlocking”.

- **Doorbell card:** each install makes a random 32-byte inbox secret and a 32-byte inbox key (app-private storage; new ones on Reset key). Its inbox ID is SHA-256("secretmessage inbox id v1" ‖ secret), first 16 bytes, which the relay can check without storing anything. The ID and the key travel only inside an open MLS chat (payload kind 5), so only a phone that passed the safety-code check (or a remembered key) learns them.
- **Ring:** pair key = HMAC-SHA256(key = both inbox keys in sorted order, "secretmessage pair v1"); pair ID = HMAC(pair key, "kid"), first 8 bytes; ring = pair ID ‖ 12-byte nonce ‖ AES-256-GCM(HMAC(pair key, "ring key"), room ‖ token ‖ time, associated data = the recipient's inbox ID). The receiver accepts it only from a remembered phone's pair key, within ±5 minutes of its clock, and once (nonces are remembered for 10 minutes). The relay cannot read, fake or redirect a ring; it sees the pair ID (stable for a pair of phones), the inbox ID and both IP addresses.
- **Auto-confirm:** when the native session reports the other phone's key as KNOWN, the app answers the safety-code prompt itself; NEW and CHANGED keys still need both people. This removes the human check for remembered keys only; key continuity is the identity check.
- **Presence:** `GET /v1/inbox/<id>/presence` tells anyone who knows an inbox ID whether that phone is ready now. Inbox IDs are shared only with remembered phones.
- **Notifications:** the chat request says only “Someone you remember wants to chat” (public version “New chat request”); the caller's name appears inside the app. The room and token stay in the app process; the notification refers to the request by a random ID.
- **Both phones calling:** in the owner's first two-phone test both phones tapped Chat at once and each dropped the other's call. Now the phone with the lower device ID joins the other's call (`RingPolicy`), and answering stops a phone's own waiting first.

### Candidate transport

Use WebRTC DataChannels for direct device-to-device traffic, with ICE/STUN and a self-controlled TURN service as a fallback. WebRTC provides transport encryption (DTLS) for DataChannel packets, but transport protection alone does not verify that the connected peer is the intended human/device. Keep an application-layer authenticated E2EE session bound to the QR-verified identity. A TURN relay should forward ciphertext only and discard it immediately; the signaling service may hold only ephemeral invitations, public connection descriptions and ICE candidates in memory. No server-side message queue or history.

Apart from the test relay above, which forwards a TEST build's MLS bytes rather than WebRTC setup data, no signaling or TURN service is implemented or deployed in this checkout. A future service must forward only short-lived SDP/ICE setup data, keep no message queue/history, use an owner-controlled TURN relay, and receive its own operational hardening, abuse/privacy, metadata-retention, and security review before deployment. The current Android preview has no network client and requests no network permissions.

- WebRTC protocol stack reference: <https://github.com/webrtc-rs/rtc>
- Android WebRTC package candidate: <https://github.com/webrtc-sdk/android>

No Android WebRTC client dependency has been selected or integrated. Before adding one, review its exact native AAR provenance, bundled third-party notices, maintenance/security backports, runtime quality, and license. Do not ship with a random public STUN/TURN service as a hidden dependency. The service operator, retention, IP/metadata exposure, abuse controls and costs must be decided and disclosed. The chosen direct-first design must explain that CGNAT, carrier networks and restrictive Wi-Fi can prevent a direct connection, and provide the approved encrypted TURN fallback without adding offline queues.

## Key and message lifecycle (planned)

1. Create a per-install identity key and protect private key material using Android Keystore where supported. Keep keys and minimum ratchet/session state separate from message content; device identity must not silently change after app restart.
2. Pair by scanning a QR code or comparing a safety phrase in person/over a trusted separate channel. Show a persistent warning if the peer key changes; never auto-accept a changed key.
3. Authenticate a fresh session handshake, then encrypt text/drawing before it enters the data channel. Test replay, reordering, duplicate, truncation, reconnect, stale invite and peer-key-substitution cases.
4. Send only while both users have an established authenticated session. No offline queue. Begin the recipient's user-selected, non-disableable 60–300-second expiry only after successful authenticated delivery and display, then clear both views at the same deadline, on chat close or session end. If delivery never completes, discard the sender's pending copy after 30 seconds.
5. Keep message bodies/strokes out of disk, saved instance state, clipboard, notification preview, logs, crash reports and backups. Clear mutable buffers on a best-effort basis; JVM/Android memory wiping cannot be guaranteed.
6. The current Android preview implements only local UI, timer and app-lock behavior. It requests no runtime permissions; AndroidX Biometric adds only install-time `USE_BIOMETRIC`/`USE_FINGERPRINT` for the optional local lock. Manifest removal rules keep network, camera, microphone, storage, contacts, location, Bluetooth and notification permissions out of the merged APK. It has no network transport, identity keys, QR scanner, notification posting, camera, microphone, or contacts access. Only three non-content settings are stored in app-private preferences (view timer, tone, app-lock switch), and they are excluded from backup and device transfer. Add only the network permissions actually required by a future reviewed WebRTC/signaling client.
